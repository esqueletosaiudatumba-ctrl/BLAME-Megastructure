## Mod jar: the remaining blocker

The handoff zip had **no `mod/build.gradle`**. I reconstructed it, got MC 1.12.2 resolving
(`minecraft { version = '1.12.2' }` in build.gradle — RFG 2.x reads the version from the extension,
not `gradle.properties`; the plugin id is `com.gtnewhorizons.retrofuturagradle`, and the marker group
must be allow-listed in `mod/settings.gradle`).

It now fails in `:compilePatchedMcJava` — compiling *Minecraft's own* sources, before our code is
ever reached. Two independent causes:
1. Missing deps on the patched-MC compile classpath: `tv.twitch.*`, `org.apache.logging.log4j.core.helpers`.
2. **The decompiled `WorldSettings.java` is missing its inner `GameType` enum** (referenced by ~55 MC
   files, including `ServerConfigurationManager` and the netty packets). RFG's MCP patch archives for
   `mcp_stable_39-1.12` are not restoring it, so the source tree is inconsistent.

Trying RFG 2.0.6 → 1.4.9 does not help; both fail identically.

Options, in order of promise:
- Get a working CleanroomMC TemplateDevEnv `build.gradle` for **Forge 1.12.2** (the stack this project
  pins: Forge 14.23.5.2860, mappings stable_39) and diff against `mod/build.gradle`.
- Patch the decompiled sources: a Gradle step that appends the `GameType` enum to
  `build/rfg/minecraft-src/java/net/minecraft/world/WorldSettings.java` and puts `tv.twitch:twitch:6.5`
  + `log4j-core` on the patched-MC compile classpath.
- Use a stock ForgeGradle environment instead.

**Never** mix the old `dist/blamegen-1.0.0.jar` (v1) with the v3/v4 core: `Mat.COUNT` is a
`static final` compile-time constant, so v1 + v3 = `ArrayIndexOutOfBoundsException` in `buildStates()`
at world creation.

## The FML "missing registries" crash (fixed this session)

Symptom, on loading `BLAME_Infinite_Megastructure`:

    Forge Mod Loader detected missing/unknown registrie(s).
    There are 2 missing registries in this save.
    cubicchunks:storage_format_provider_registry
    cubicchunks:vanilla_compatibility_generators_registry

**Cause.** The shipped save's `level.dat` carries FML registry entries (in `Data.fml.Registries`)
for those two names. Those strings *do* exist in the class files of CubicChunks **0.0.1301.0**
(verified: in `StorageFormatProviderBase` / `VanillaCompatibilityGeneratorProviderBase`), but that
build does **not register them as FML registries** - the namespaced-registry form belongs to a
newer CubicChunks. So Forge sees registry data in the save with no matching registry and blocks
the load. The bundled CC 0.0.1301.0 jar is what the HANDOFF documents and what the earlier server
test used, so the fix belongs on the save, not the jar.

**Fix.** `tools/verify/NbtRegistryFix.java` (new, pure Java, no Minecraft) removes exactly those two
keys from `Data.fml.Registries` in a `level.dat`, leaving the rest of the file untouched.
Idempotent and safe to re-run.

    java -cp build/fix NbtRegistryFix <path/to/level.dat> [more...] [--dry]

Verified on this machine: the shipped save
(`instance/minecraft/saves/BLAME_Infinite_Megastructure/level.dat`) rewrites 12427 -> 12474 bytes
with both keys gone and `Data.fml`, `LevelName` and everything else intact; a follow-up `--dry`
run reports clean. The same fix has been applied to all three ElyPrism instances on this PC.
Clicking "Yes" on the prompt also removes the entries, but doing it explicitly is cleaner and
works for instance zips you cannot click through.
